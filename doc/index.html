1. 構成

  • バックエンド（Linux専用）がSDK2を介してカメラを所有します。SDKはスレッドセーフでないため、すべてのSDK呼び出しは1本のengineスレッドで行います。
  • 制御チャネル：ZeroMQ ROUTER。要求は JSON、fetch の応答はフレームごとにバイナリ部を付けて返します（ゼロコピー）。wait は非同期に応答するため、待機中も他のクライアントは止まりません。
  • データチャネル：ZeroMQ PUB。全フレームをヘッダ JSON + 生データ（uint16, little endian, 行優先）で配信し、0.5 秒ごとに status も配信します。遅い購読者のキューは publish_hwm フレームで頭打ちになり、カメラ側は止まりません。
  • 同一ホストのクライアントは /run/andor-emccd の Unix ドメインソケット（IPC）を自動で使い、ネットワークスタックを通りません。他ホストは TCP です。
  • カメラが開けない場合（ドライバ未ロードなど）もサービスは動き続け、status に disconnected と SDK のエラーを出して 30 秒ごとに再試行します。
  • 停止時は、冷却中なら -20 °C まで昇温してから ShutDown します（cooler_persist_on_shutdown または warmup_on_exit: false で無効）。

2.2 Andor SDK とPCIドライバ

SDK 2.103（andor-2.103.30058.0.tar.gz）を使ってください。Andor から届いたこの版には PCI ドライバのソース src/driver（andordrvlx、GPL-2.0）が含まれています。install_andor もドライバをビルドし、カーネル 3 以降では Makefile5.4（M= 形式）を使います（2026-10-16 確認）。

SDK 2.104（andor-2.104.30088.0.tar.gz）にはドライバが入っていません。tar の中にもともと src/ が無く、解凍方法のせいではありません。install_andor にもドライバを扱う処理がありません。ドライバと libandor.so は同じ版を組み合わせるため、カメラPCには 2.103 一式を入れます。2.104 のヘッダとの違いは、追加された関数 3 つ（GetMetaData、LoadEEPROM、SetKeepCleanMode）だけです。このプログラムはこれらを使っていないので、2.103 でもそのままビルドできるはずです（ヘッダの比較による確認。2.103 でのビルドはまだ試していません）。

7-Zip（Windows）で解凍すると、tar 内の python/ と Python/ が 1 つの python/ にまとまります。中身は失われていないので問題ありません。Linux では tar -xzf で解凍してください。

2.103 のドライバとカーネル 5.14：ソースを読んで確認しました（この PC ではビルドしていません）。andorcompat.h と fault.c に新しいカーネル向けの分岐があり、get_num_physpages()、vm_fault_t、file_inode()、unlocked_ioctl、VM_RESERVED の代替定義、IRQF_DISABLED の削除に対応済みです。AlmaLinux 9（5.14）ではそのままビルドできる見込みです。ただし、カーネル 6.3 以降（AlmaLinux 10 など）では vma->vm_flags |= がビルドエラーになり、vm_flags_set() への置き換えが必要です。

コントローラカード：このカメラのカードは CCI-24 です。ドライバは Andor のベンダー ID 0x149a のデバイスを、デバイス ID に関係なくすべて拾います。カードの種類（PCI3233、PCI3266、PCIe3201）は PLD のデバイス ID で判別します。lspci -nn -d 149a: と dmesg | grep andordrvlx（「Device ID ...」の行）で、認識されたことを確認してください。

DMA モード（iXon は DMA_MODE=1 が必須）：INSTALL の「Large DMA Transfers」によると、ドライバには 1 行ずつ転送するモード（DMA_MODE=0）と 1 画像ずつ転送するモード（DMA_MODE=1）があり、iXon では DMA_MODE=1 しか使えません。install_andor でも iXon を選ぶと DMA_MODE=1 になります。DMA_MODE=1 では、2 画像 × 4 バイト/画素ぶんの物理メモリ（897 では 2 MB）をドライバ専用に確保します。PCI カードは 4 GB より上のアドレスを扱えません。

2.103 の andor.c では、DMA_ADDRESS を省略すると、バッファの物理アドレスを get_num_physpages()*PAGE_SIZE（RAM の総ページ数 × ページサイズ）として計算します。最近の PC は 4 GB 未満に PCI 用の穴があり、RAM が 4 GB より上にも置かれるので、この値は「RAM の末尾」になりません。そのため、このままでは使えません。確保の方法には次の 3 つがあります。

  1. mem=（Andor の標準の方法）：カーネルが使うメモリを制限し、その上をドライバに使わせます。4 GB 未満にしか置けないため、RAM が 3 GB を超える PC では残りの RAM が使えなくなります。現代の PC には向きません。
  2. memmap=8M$0x40000000 で予約し、DMA_ADDRESS で渡す方法：使わないでください。カメラPCで grubby により memmap=8M\$0x40000000 を設定したところ、GRUB の $ の扱いのために、カーネルには実質 memmap=8M（RAM を 8 MB に制限）として渡り、起動が止まりました（2026-10-16。GRUB の編集画面で引数を消して復旧）。
  3. ドライバで確保する（採用）：ドライバのパッチ（Andor のドライバソースの差分なので、このリポジトリには含めていません）は、DMA_MODE=1 かつ DMA_ADDRESS=0 のとき、2 つの画像バッファを dma_alloc_coherent で確保します。32 ビットの DMA マスクを設定するので、バッファは 4 GB 未満に置かれます。カーネルの起動オプションは要りません。大きさは DMA_SIZE（MB、2 つのバッファの合計）で決まり、DMA_SIZE=4 で 1 つ 2 MB です（897 の全画面は 1 MB）。あわせて、ドライバが行っていなかったバスマスタの有効化（pci_set_master）も加えています。IOMMU が有効な PC でも、DMA API が返すアドレスを渡すので正しく動きます。

その他の注意：

  • モジュールの読み込み：install_andor は /etc/andordrvlx_load DMA_MODE=1 を /etc/rc.d/rc.local に書きますが、同時にプロンプトの出力（more の出力やパイプで渡した答え）を #!/bin/bash の前に書き込むため、起動時に「Exec format error」で失敗し、再起動後にドライバが読み込まれません。tools/camera_pc/25_driver_service_root.sh（20 番の最後でも実行）が rc.local を直して Andor の行を除き、代わりに systemd の andordrvlx.service で読み込みます。バックエンドのサービスはこの後に起動します。ロードスクリプトは modprobe を使うので、/etc/modprobe.d/andordrvlx.conf の options が反映されます。デバイスファイルはロードスクリプトが mknod で作ります。
  • Detector.ini：古い CCD 用の CodeFile 指定で、iXon は不要です。
  • Secure Boot：有効な場合、自作モジュールには署名（mokutil）が必要です（試験したカメラPCでは無効）。

3. 設定変更権

複数のクライアントが同時に設定を変えないよう、バックエンドが「設定変更権」を1つだけ発行します。認証はありません。

  • 変更系のコマンド（set_settings, start, arm, stop, software_trigger）は変更権を持つクライアントだけが実行できます。それ以外のクライアントは code: "not_controller" で拒否されます。読み出し系（get_*, fetch, wait, ライブ配信）は誰でも使えます。
  • 変更権は acquire_control で要求し、空いていればバックエンドが承認します。他のクライアントが持っていれば code: "control_denied" と持ち主を返します。force: true で奪えます（GUI は確認ダイアログを出します）。release_control で手放します。
  • 各クライアントは起動ごとのランダムな ID と名前を全要求に付けます。表示名は 名前@IP、名前が空なら client@IP。IP は TCP ならバックエンドが見た接続元アドレス、同一ホスト（IPC）ならクライアントが申告した LAN 側アドレスです。
  • 持ち主は status の control（{"holder", "holder_id", "since"} または null）で全クライアントに配信され、GUI の Status に表示されます。
  • 持ち主が落ちても権利が残らないよう、持ち主は 2 秒ごとに keepalive を送り、control_lease_s（既定 10 秒）途絶えると自動で解放されます。GUI と Python クライアントは自動で keepalive を送ります。

同じマシンで GUI を 2 つ起動することはできません。クライアントは connect するだけで送信元ポートは毎回 OS が割り当てるため、ポートのバインドで自然に防がれることはありません。そこで GUI は起動時に 127.0.0.1:47109 を自分でバインドし、2 つ目はこのバインドに失敗して終了します（マシン全体で有効。異常終了してもOSが解放）。

9. 実機で確認すること

コードは SDK 2.104 のヘッダとマニュアルに沿って書き、Fable 5.1 によるレビューを反映済みです。マニュアルから決められない点は実機で確認してください。

  1. ドライバ：andordrvlx のビルドとロード、/dev/andordrvlx0 の権限（andor グループ）。journalctl -u andor-emccd-backend に camera: iXon ... serial ... が出ること。
  2. 取得の基本：internal / continuous で Live、single、kinetic N 枚が期待どおりのフレーム数になること（GUI の Status と get_runs）。
  3. GetImages の範囲：GetNumberNewImages の番号が run ごとに 1 から始まること。「circular buffer overrun」「GetImages returned ... retrying」の警告がログに出ないこと（出た場合は報告を）。
  4. メタデータ時刻：camera_time_s が null でなく、フレーム間隔がサイクル時間に一致すること（GetMetaDataInfo の番号の基準が未記載のため、0 始まりを先に試し、だめなら 1 始まりを使う実装）。CCI-23 でメタデータが使えるかも確認。
  5. 累積モード：accumulate N 回で 1 枚の int32 の和が返ること（GetAcquiredData）。
  6. 外部トリガ：external（各エッジで露光）、external_start、external_exposure（パルス幅が露光時間。frame transfer は機能ビットが無ければ自動で off）、fast_external_trigger、trigger_invert。labscript からの arm → トリガ → 取得。
  7. ソフトウェアトリガ：continuous モードでのみ有効（SDK の制約）。
  8. Isolated crop：同じ大きさの通常のサブ画像より速くなること、画像の大きさが一致すること、切り出す角の位置。
  9. EM ゲイン：モードごとの範囲（get_info の em_gain_range）と、advanced の可否。オフ（最小値）で信号が通常アンプ相当になり、オンで設定値どおりに増えること。
  10. シャッタ：外部シャッタの TTL（SetShutterEx / SetShutter を機能ビットで選択）。
  11. 冷却：目標温度への到達と安定（status の色）、取得中も温度が読めるか（読めない機種は直前の値を保持）。サービス停止時に -20 °C まで昇温してから ShutDown すること（2 回目のシグナルで中断）。起動時、冷却が動いていればそのまま維持すること。
  12. カウント変換：electrons / photons で int32 データが返ること。
  13. 性能：全画面 10 MHz で約 35 fps、クロップ時のフレームレート、LAN 経由の取りこぼし 0。

12. リングバッファとクライアント別の欠落通知

サーバーは backend.json の history_frames（既定2000）と history_megabytes（既定2048）で履歴の長さを設定できます。 フレーム数またはメモリ量の上限で古いフレームを上書きします。メモリ量0は容量制限なしで、 1枚が上限より大きい場合も最新の1枚を保持します。

GUIの接続画面の Client buffer (frames) または起動時の --buffer-frames 64 でクライアントのリング長を指定します。既定は64枚です。 受信と画像処理は別スレッドで動き、処理が遅くて満杯になった場合は最も古い未処理フレームを上書きします。 GUIの dropped はサーバー側とクライアント側の欠落合計です。フレームレート欄のツールチップに直近の処理フレームの通知を表示します。

from andor_emccd.client import FrameSubscriber
sub = FrameSubscriber("camera-pc", buffer_frames=128)
try:
    item = sub.recv(timeout_s=5)
    if item and item[0] == "frame":
        _, header, image = item
        print(header["delivery"]["server_loss"])
        print(header["delivery"]["client_loss"])
finally:
    sub.close()

各フレームの delivery は server_loss と client_loss を含みます。 count は前回の通知からの欠落数で、欠落なしでも必ず0を通知します。 欠落時には first_seq、last_seq、first_timestamp、 last_timestamp を付けます。時刻は欠落したフレームの取得時刻（Unix秒）、 reported_at は通知を作った時刻です。連番はrunをまたぐサーバー全体の番号です。 カメラSDKがサーバー取得前に失ったフレームは、この通知の対象外です。

プロトコルと送信位置

GUIとPythonのFrameSubscriberは制御ポートのROUTER/DEALERで受信します。 stream_open が確立した時点の次のフレームから読み始め、接続前の履歴は fetch で取得します。各接続インスタンスの一意なclient IDを使い、送信位置を独立に保持します。 古いPUB/SUB配信も互換性のため残しています。

要求動作
stream_open送信位置を登録。同じIDでの再要求は位置をリセットしません。
stream_read {count: 8, ack: 0}最大count枚（1〜256）と、常に loss、next_seq、batch_id を返します。バイナリは既存fetchと同じ形式です。
stream_read {count: 8, ack: batch_id}直前の受信を確認して次のバッチへ進みます。確認されていないバッチは同じ内容を再送します。
stream_close送信位置と再送用バッチを解放します。

遅いクライアントの未送信データがサーバーのリングから消える際、そのクライアントについて欠落を記録し、次の送信で通知します。 高速なクライアントの通知には影響しません。欠落通知もバッチとともに保持され、再送で消えません。 再送用に1クライアントあたり最大16 MiB（単一フレームがそれより大きい場合はその1枚）をリング外に共有保持します。 登録上限は256、60秒間stream要求のない登録は失効します。受信エラーや失効は通知され、再接続時には新しいストリームを開きます。

C++では FrameSubscriber(context, data_endpoint, on_frame, on_status, capacity, control_endpoint) を使用し、Frame::delivery で通知を受け取ります。control_endpointを省略した旧PUB受信では サーバーがクライアント別の時刻を追跡できないため、連番から検出した欠落の時刻はnullになります。 Pythonの低水準APIは open_stream()、read_stream()、close_stream() です。 同じストリームには読み手を1つにしてください。タイムアウトしたreadを再試行すると未確認のバッチを返します。

13. クライアントでの画像の平均表示

Displayパネルの Average (frames) に、表示に使う直近の画像枚数を指定します。 受信した画像をクライアントのリングに保持し、画素ごとの移動平均を表示します。1は平均なしです。 平均枚数は1〜リング長−1に制限されます。リング長1の場合は平均なしだけを選べます。 リング長を小さくして再接続した場合も、平均枚数は新しい上限に収まります。

Images averaged は「実際に使った枚数 / 設定枚数」です。接続・撮影開始直後など、 画像がまだ十分にない場合は保持している枚数で平均します。画像のrun、サイズ、画素型、ビニング、 センサー上の位置が変わった場合は履歴をリセットし、異なる撮影条件の画像を混ぜません。 欠落がある場合はリングに実際に残っている画像を使います。平均枚数を変えると、停止中でも保持画像から再描画します。

平均は表示画像とカーソルで読み取る画素値に適用し、整数画像の端数も表示できるよう平均結果をfloat32で扱います。 ROI解析・UDP出力・フレームの記録・Save frameは元のフレームを使います。 Save viewは平均後の画面画像を保存します。サーバーの設定変更や制御権の取得は不要です。 平均枚数はクライアントの設定に保存されます。

数値平均、端数、履歴の上書き、枚数制約、run・画像位置の変更をC++テストで確認し、 模擬カメラのGUIでもリング長4・平均枚数3のライブ表示と設定保存を確認しました。 最終試験はLinux 28/28、Windows（MSVC）20/20が成功し、Windows版も更新済みです。

14. ライブ画像の逐次保存

右側の Stream recording タブで、新しい保存先の .tif ファイルと Maximum save rate (fps) を指定し、Start saving を押します。 0は受信した全フレーム、正の値はそのfps以下になるよう取得時刻を基準に間引きます。 最大fpsは撮影runごとに適用し、取得間隔の比較には1 µsの許容差を設けています。 Stop saving・切断・終了時は、書き込み待ちの画像を保存してファイルを閉じます。 設定は保存しますが、次回の起動時に自動で保存を再開することはありません。

形式は非圧縮の複数ページBigTIFFです。1ファイルに複数の生画像を逐次追記し、4 GiBを超える記録にも対応します。 表示の平均設定によらずuint16・int32・float32の元データを保存します。各ページのJSONには連番、run、 取得時刻、画像サイズ、画素型、露光・ゲインなどのフレームヘッダーと欠落通知を格納し、最初のページには開始時の設定も格納します。 撮影途中で画像サイズが変わってもページ単位で読み出せます。 tifffile公式説明、 libtiffの形式指定を参照してください。

保存は専用スレッドで行い、画面には保存済み・fpsによる間引き・保存キューあふれ・待ち枚数・失敗を表示します。 キューの上限はクライアントのリング長と256 MiBで、これに書き込み中の最大1枚が加わります。 既存ファイルは上書きしません。保存fpsは上限なので、撮影速度やディスク速度が不足すれば実際の保存fpsは低くなります。 各ページは完成後にOSへ書き出しますが、停電耐性や保存途中の同時読取を保証するものではありません。

from andor_emccd.recording import iter_recorded_frames

    print(info["frame"]["seq"], info["frame"]["timestamp"])
    print(image.shape, image.dtype)
    # 初期設定は最初のページの info["metadata"]
    print(info["recording"]["loss_since_previous_saved"])

読み出しはページ単位なので、記録全体をメモリへ読み込む必要はありません。 rate_skipped_total と queue_dropped_total は各ページを保存候補に選んだ時点の累積値です。 最後の保存ページより後の間引きはファイル内の値には含まれず、停止後の画面で最終値を確認できます。 fpsで間引いた画像に付いていた受信欠落通知も、次に保存するページへまとめて引き継ぎます。

画像と多数の解析配列を階層構造でまとめたい場合は、拡張可能なデータセットを持つ HDF5も有力です。 今回はWindowsを含む既存ライブラリで利用でき、Pythonから画像を簡単に扱えるBigTIFFを採用しました。 Linuxで34件、Windows（MSVC）で26件のテストが通過しました。 GUIでは表示を3枚平均にしたまま5 fps以下で13枚の生uint16画像を保存し、Pythonで読み戻しました。 Windowsで書いたファイルもLinuxのPythonから読み戻せることを確認済みです。

15. 小数の電子数・光子数表示と設定記録（v0.3.0）

Display conversion タブの Display units で Counts / Electrons / Photons を選びます。 Camera calibration は SDK の GetSensitivity と GetQE を使います。RealGain は設定倍率、EM off は公称1倍を使い、 実測済みの倍率とは区別して記録します。DAC・Linearモードで実倍率が不明な場合やSDKが値を返さない場合は、 Manual coefficients に切り替え、Sensitivity (e⁻/ADU)、Physical EM gain、QE (%)、Baseline (ADU) を入力してください。 Camera calibration から Manual に切り替えると直前の表示値を編集できます。

換算式は electrons = (raw − offset) × sensitivity / EM gain、 photons = electrons / QE（QEは0〜1）です。BG ROIを使う場合は、そのフレームのROI平均値がoffsetになり、 baselineを二重には引きません。カメラ側の SDK conversion (integer) は Counts に設定してください。 表示換算はfloat32で小数・負値を保ちます。通常のSave frame / Record / Stream recordingは元データを保存し、 Save converted は平均・BG補正・単位換算後、カラーマップやしきい値の適用前の値をfloat32 TIFF/FITS/NPYに保存します。 ROI統計・式・UDP出力は従来どおりraw単位です。保存係数だけでは真の整数光子数の確定はできず、換算値は推定値です。

raw TIFF各ページの analysis にはBG ROIの座標・平均・画素数と、GUI設定・使用係数・換算式を記録します。 FITS/PNGのJSONタグ、NPYの .npy.json にもメタデータを保存します。過去のバックエンド画像を後から保存した場合は、 GUI設定が保存時のスナップショットであることを明記します。新版バックエンドの各フレームヘッダーには取得時のカメラ設定も入ります。

接続した各GUIは表示・校正・ROI・式・UDP・トレンド・ウィンドウ配置などをバックエンドへ通知します。 BLACSはbuffered移行時のスナップショットを、data/<device>/camera/images/gui_settings_snapshot にJSONとして保存します。 micro0とgen0のGUIは別プロファイルとして、送信元・更新時刻とともに記録します。カメラ由来の係数はそのショットの実際の設定で再取得し、 各フレームのBG平均と換算情報を frame_display_metadata に保存します。raw画像はCountsで保存し、PNG/HDF5プレビューも生成します。 これはコンパイル時ではなく実行時の記録です。バックエンド起動後に接続していないGUIの設定は取得できません。 旧版バックエンドで設定取得APIが使えない場合は、その旨を記録し、raw取得は継続します。
