1. Architecture

  • The backend (Linux only) owns the camera through SDK2. The SDK is not thread-safe, so all SDK calls run on a single engine thread.
  • Control channel: ZeroMQ ROUTER. Requests use JSON; fetch replies include a binary part for each frame, without copying the image data. Replies to wait are asynchronous, so other clients remain responsive.
  • Data channel: ZeroMQ PUB. Every frame is published as a JSON header and raw pixels (uint16, little-endian, row-major), with status published every 0.5 seconds. Slow subscribers have a queue limit of publish_hwm frames and do not block the camera.
  • Local clients automatically use Unix domain sockets (IPC) under /run/andor-emccd, bypassing the network stack. Remote clients use TCP.
  • If the camera cannot be opened, for example because the driver is not loaded, the service stays running. Status reports disconnected and the SDK error, and the backend retries every 30 seconds.
  • On shutdown, a cooled sensor is warmed to -20 °C before ShutDown. This is disabled by cooler_persist_on_shutdown or warmup_on_exit: false.
  • The backend monitors sensor temperature, the head's cooling-control circuit temperature, and TE cooler voltage. Loss of cooling raises an alarm in the log and status. Configure telemetry to send measurements to Telegraf for viewing in Grafana (section 15).

2.2 Andor SDK and PCI driver

Use SDK 2.103 (andor-2.103.30058.0.tar.gz). This distribution from Andor includes the PCI driver source in src/driver (andordrvlx, GPL-2.0). Its install_andor script builds the driver and uses Makefile5.4 with the M= syntax for kernels 3 and later (checked on 2026-10-16).

SDK 2.104 (andor-2.104.30088.0.tar.gz) does not include the driver. The archive itself has no src/ directory; this is not an extraction issue. Its install_andor script has no driver installation logic either. Use the complete 2.103 distribution on the camera PC so that the driver and libandor.so versions match. The only additions in the 2.104 header are GetMetaData, LoadEEPROM, and SetKeepCleanMode. This program does not use them, so it was expected to build unchanged with 2.103 (based on a header comparison; a 2.103 build had not yet been tested at that point).

When 7-Zip extracts the archive on Windows, python/ and Python/ merge into one python/ directory. No contents are lost. On Linux, extract with tar -xzf.

The 2.103 driver and kernel 5.14: source inspection, without a build on the development PC, found compatibility branches in andorcompat.h and fault.c for get_num_physpages(), vm_fault_t, file_inode(), unlocked_ioctl, replacement definitions for VM_RESERVED, and removal of IRQF_DISABLED. It was expected to build unchanged on AlmaLinux 9 (5.14). On kernels 6.3 and later, including AlmaLinux 10, vma->vm_flags |= causes a build error and must be replaced with vm_flags_set().

Controller card: this camera uses a CCI-24. The driver matches all devices with Andor vendor ID 0x149a, regardless of device ID. It identifies the card type (PCI3233, PCI3266, or PCIe3201) from the PLD device ID. Check detection with lspci -nn -d 149a: and the “Device ID ...” line in dmesg | grep andordrvlx.

DMA mode (iXon requires DMA_MODE=1): the INSTALL section “Large DMA Transfers” describes transfers by row (DMA_MODE=0) and by image (DMA_MODE=1). iXon only supports DMA_MODE=1, which install_andor selects for iXon. This mode reserves physical memory for two images at four bytes per pixel (2 MB for the 897). The PCI card cannot address memory above 4 GB.

In 2.103's andor.c, omitting DMA_ADDRESS sets the physical buffer address to get_num_physpages()*PAGE_SIZE (total RAM pages times page size). Modern PCs have a PCI memory hole below 4 GB and RAM above 4 GB, so this does not identify the end of RAM and cannot be used as-is. There are three allocation approaches:

  1. mem= (Andor's standard approach): restrict the memory available to the kernel and let the driver use memory above that limit. Because the buffers must be below 4 GB, PCs with more than about 3 GB lose access to their remaining RAM. This is unsuitable for modern PCs.
  2. Reserve memory with memmap=8M$0x40000000 and pass DMA_ADDRESS: do not use this approach. Setting memmap=8M\$0x40000000 with grubby on the camera PC caused GRUB's handling of $ to pass effectively memmap=8M to the kernel, limiting RAM to 8 MB and preventing boot (2026-10-16; recovered by removing the argument in GRUB's editor).
  3. Allocate in the driver (implemented): the driver patch, which is not distributed here because it contains changes to Andor's source, allocates two image buffers with dma_alloc_coherent when DMA_MODE=1 and DMA_ADDRESS=0. A 32-bit DMA mask keeps their addresses below 4 GB. No kernel boot arguments are needed. DMA_SIZE specifies the combined buffer size in MB; DMA_SIZE=4 gives two 2 MB buffers (a full 897 image occupies 1 MB in this format). The patch also enables bus mastering with pci_set_master, which the original driver omitted. Passing the address returned by the DMA API also supports systems with an IOMMU.

Additional notes:

  • Module loading: install_andor adds /etc/andordrvlx_load DMA_MODE=1 to /etc/rc.d/rc.local, but also writes prompt output, including more output and piped answers, before #!/bin/bash. This produces “Exec format error” at boot and leaves the driver unloaded. tools/camera_pc/25_driver_service_root.sh, also run at the end of script 20, repairs rc.local, removes the Andor entry, and loads the driver through andordrvlx.service instead. The backend service starts afterward. The loader uses modprobe, so it honors options in /etc/modprobe.d/andordrvlx.conf. It creates device files with mknod.
  • Detector.ini: specifies a CodeFile for older CCDs and is not needed for iXon.
  • Secure Boot: custom modules must be signed using mokutil when Secure Boot is enabled. It was disabled on the tested camera PC.

3. Control ownership

The backend grants control to one client at a time to prevent conflicting changes. There is no authentication.

  • Only the controller can issue commands that change camera state (set_settings, start, arm, stop, software_trigger). Other clients receive code: "not_controller". Read operations (get_*, fetch, wait, and live streaming) are available to all clients.
  • Request control with acquire_control. If unclaimed, the backend grants it; otherwise it returns code: "control_denied" and the current holder. Use force: true to take over; the GUI asks for confirmation. Release it with release_control.
  • Each client includes a random ID generated at startup and a name in every request. The display name is name@IP, or client@IP if unnamed. For TCP, the IP is the peer address seen by the backend; for local IPC, it is the LAN address reported by the client.
  • Status broadcasts the owner to all clients in control ({"holder", "holder_id", "since"} or null). The GUI shows it in Status.
  • The controller sends a keepalive every 2 seconds. If none arrives within control_lease_s (default 10 seconds), the backend releases control, preventing a crashed client from retaining it. GUI and Python clients send keepalives automatically.

Only one GUI instance can run on a machine. Normal client connections use OS-assigned source ports, so they do not prevent duplicate instances. The GUI therefore binds 127.0.0.1:47109 at startup; a second instance fails to bind and exits. This lock applies across the machine and is released by the OS after a crash.

5. Python API and labscript

pip install ./python            # numpy, pyzmq
from andor_emccd import AndorEMCCDClient, FrameSubscriber, WaitTimeoutError
cam = AndorEMCCDClient("camera-pc", name="analysis")  # Automatically selects IPC for a local host
cam.acquire_control()                         # ControlDeniedError if another client holds control
cam.set_settings(exposure_time_s=0.005, trigger_mode="external",
                 em_gain_enabled=True, em_gain=100)   # EM gain defaults to off
run = cam.arm(n_frames=3)                     # Arm three kinetic frames for triggering
cam.wait(run["run_id"], timeout_s=10)         # WaitTimeoutError if frames do not arrive
images, headers = cam.fetch(run["run_id"])   # (3, 512, 512) uint16
cam.get_status()["temperature_c"]
cam.release_control()                         # close() also releases control

sub = FrameSubscriber("camera-pc")          # Receive live frames
topic, header, image = sub.recv(timeout_s=1.0)

The client is locked during wait. Use a second client to send stop or other commands while waiting. fetch(..., stack=False) returns a list of views without copying and is about twice as fast for large runs.

The worker requests control before operations that change camera state; its default name is labscript. If the GUI holds control, the shot fails with ControlDeniedError and identifies the holder. Set force_control=True in the connection table to take over.

In transition_to_buffered, it calls arm for the shot's frame count. In grab_multiple, it retrieves arriving frames and saves them to HDF5.

Enabling/disabling EM gain: with em_gain_enabled=false, the backend passes the minimum for the current mode to SetEMCCDGain (0 in DAC modes for no multiplication, or 1 in linear/real-gain modes), while retaining the em_gain setpoint. Gain defaults to off to reduce gain-register degradation under bright illumination. Changing only em_gain while disabled saves the setpoint but returns a warning. The conventional amplifier (output_amplifier=1) does not apply EM gain.

9. Hardware verification

The code was written against the SDK 2.104 headers and manual and incorporates a Fable 5.1 review. Verify behavior that the manual does not establish on the actual camera.

  1. Driver: build and load andordrvlx, check /dev/andordrvlx0 permissions for the andor group, and confirm camera: iXon ... serial ... in journalctl -u andor-emccd-backend.
  2. Basic acquisition: verify Live in internal/continuous mode, single frames, and N-frame kinetic runs using GUI Status and get_runs.
  3. GetImages ranges: verify that GetNumberNewImages indices restart at 1 for each run. Report any “circular buffer overrun” or “GetImages returned ... retrying” log warnings.
  4. Metadata timestamps: verify non-null camera_time_s and frame intervals matching the cycle time. Because the index base of GetMetaDataInfo is undocumented, the implementation tries zero-based indices first, then one-based indices. Also check metadata availability on CCI-23 hardware.
  5. Accumulation: accumulating N exposures should return one int32 sum through GetAcquiredData.

Display correction using a background ROI

Check BG for one ROI in Analysis and enable its On checkbox. Enable Subtract background ROI in Display to subtract that ROI's mean from every displayed pixel. This is applied after display averaging and before thresholding or colormapping, preserving negative values. Invalid or out-of-image ROIs disable correction and show an explanation.

ROI statistics, formulas, UDP output, and saved raw pixels remain based on the received data. Each frame receives background ROI coordinates, mean, sum, and pixel count in analysis.background, stored in TIFF ImageDescription, PNG Description, FITS COMMENT, or an NPY .npy.json sidecar. Every stream-recording TIFF page includes its own background metadata. After changing image size or binning, check the ROI bounds: coordinates are interpreted in pixels of the new image. Here, raw means pixels received from the backend. If SDK Count Convert is enabled, those received pixels have already been converted to integer electrons or photons.

12. Ring buffers and per-client loss notifications

Configure server history with history_frames (default 2000) and history_megabytes (default 2048) in backend.json. Old frames are overwritten when either limit is reached. A memory limit of 0 means unlimited. The latest frame is retained even if it alone exceeds the limit.

Set the GUI client's ring capacity using Client buffer (frames) in the connection dialog or --buffer-frames 64 at startup; the default is 64 frames. Reception and image processing run on separate threads. If processing falls behind and the ring fills, the oldest unprocessed frame is overwritten. The GUI's dropped count combines server and client losses. The frame-rate tooltip shows notifications from the most recently processed frame.

from andor_emccd.client import FrameSubscriber
sub = FrameSubscriber("camera-pc", buffer_frames=128)
try:
    item = sub.recv(timeout_s=5)
    if item and item[0] == "frame":
        _, header, image = item
        print(header["delivery"]["server_loss"])
        print(header["delivery"]["client_loss"])
finally:
    sub.close()

Each frame's delivery contains server_loss and client_loss. count is the loss since the previous notification and is explicitly 0 when no frames were lost. Loss notifications include first_seq, last_seq, first_timestamp, and last_timestamp. Timestamps are the lost frames' acquisition times in Unix seconds; reported_at is when the notification was created. Sequence numbers span all runs on the server. Frames lost inside the camera SDK before server acquisition are outside these notifications.

Protocol and delivery cursors

The GUI and Python FrameSubscriber receive frames through ROUTER/DEALER on the control port. Reading starts with the first frame after stream_open succeeds; use fetch for earlier history. Each connection instance has a unique client ID and an independent delivery cursor. Legacy PUB/SUB streaming remains available for compatibility.

RequestBehavior
stream_openRegisters a delivery cursor. Repeating it with the same ID does not reset the cursor.
stream_read {count: 8, ack: 0}Returns up to count frames (1–256), always including loss, next_seq, and batch_id. Binary parts use the existing fetch format.
stream_read {count: 8, ack: batch_id}Acknowledges the previous batch and advances to the next. An unacknowledged batch is retransmitted unchanged.
stream_closeReleases the delivery cursor and retransmission batch.

When unsent data for a slow client leaves the server ring, the server records that client's loss and reports it on the next delivery. Other, faster clients are unaffected. Loss notifications remain attached to retained batches and survive retransmission. Each client can retain up to 16 MiB of shared frame references outside the ring for retransmission, or one frame if larger. There are at most 256 registrations; a registration expires after 60 seconds without a stream request. Receive errors and expiry are reported, and reconnection opens a new stream.

In C++, use FrameSubscriber(context, data_endpoint, on_frame, on_status, capacity, control_endpoint) and read notifications from Frame::delivery. Legacy PUB reception without control_endpoint detects sequence gaps, but loss timestamps are null because the server cannot track each client's delivery history. Python's low-level API provides open_stream(), read_stream(), and close_stream(). Use one reader per stream. Retrying a timed-out read returns the unacknowledged batch.

Test configuration is in deploy/stream-test.json. C++ and Python tests on Linux and Windows cover independent cursors, exact timestamps for overwritten history, zero-loss reports, receiver-ring overwrites, and retransmission of unacknowledged batches.

Results on 2026-10-18: Linux C++ 25/25 and Windows MSVC C++ 17/17 passed. Python integration tests passed on both platforms, verifying two lost server frames and their timestamps, 18 lost frames in a receiver ring of capacity two, a subsequent zero-loss report, and retransmission. Windows used an SSH reverse tunnel. The local GUI also displayed the simulator at about 49 fps with zero losses.

13. Client-side display averaging

Set Average (frames) in Display to the number of recent frames to average. Received images are retained in the client ring and displayed as a per-pixel moving average; 1 disables averaging. The allowed range is 1 to ring capacity minus 1. A ring capacity of 1 permits only no averaging. Reconnecting with a smaller ring also clamps the averaging count to the new limit.

Images averaged shows the actual count used / requested count. Immediately after connecting or starting acquisition, fewer frames may be available, so the average uses those retained. History resets when the run, image dimensions, pixel type, binning, or sensor position changes, preventing incompatible images from being mixed. After losses, averaging uses the frames actually retained. Changing the count redraws retained frames even while acquisition is stopped.

Averaging affects the displayed image and cursor pixel values. Results use float32 to preserve fractions from integer images. ROI analysis, UDP output, frame recording, and Save frame use the original frames. Save view exports the averaged display. No server setting changes or control ownership are required. The averaging count is saved in client preferences.

C++ tests cover numerical averages, fractions, overwritten history, count limits, and changes in run or image position. Simulator GUI tests verified live display and persistence with a ring capacity of 4 and averaging count 3. At this feature's validation, Linux 28/28 and Windows MSVC 20/20 tests passed, and the Windows installation was updated.

14. Stream recording

In the right-hand Stream recording tab, choose a new .tif destination, set Maximum save rate (fps), and press Start saving. A value of 0 saves every received frame. Positive values subsample by acquisition timestamp to stay at or below the limit. The limit is applied separately for each run, with a 1 µs tolerance when comparing intervals. Stop saving, disconnecting, or exiting drains queued images and closes the file. Settings persist, but recording does not automatically resume on the next launch.

The format is uncompressed multipage BigTIFF. Raw frames are appended to one file, including recordings above 4 GiB. Original uint16, int32, or float32 pixels are saved regardless of display averaging. Each page's JSON contains sequence/run identifiers, acquisition time, dimensions, pixel type, exposure, gain, other frame-header fields, and loss notifications. The first page also includes the initial settings. Pages remain individually readable if image dimensions change during recording. See the tifffile documentation and libtiff format options.

A dedicated thread writes images. The UI reports saved frames, rate-skipped frames, queue drops, pending frames, and failures. The queue is bounded by both client ring capacity and 256 MiB, plus at most one frame being written. Existing files are never overwritten. The fps setting is an upper limit; acquisition or disk throughput can reduce the actual rate. Each completed page is flushed to the OS, but power-loss resilience and concurrent reads during recording are not guaranteed.

# Install once for Python reading: pip install tifffile
from andor_emccd.recording import iter_recorded_frames
for image, info in iter_recorded_frames("recording.tif"):
    print(info["frame"]["seq"], info["frame"]["timestamp"])
    print(image.shape, image.dtype)
    # Initial settings are in info["metadata"] on the first page
    print(info["recording"]["loss_since_previous_saved"])

Reading is page-by-page and does not require loading the entire recording into memory. rate_skipped_total and queue_dropped_total are cumulative values when each page was selected for saving. Skips after the last saved page are not reflected in the file; final totals remain visible in the UI after stopping. Receive-loss notifications attached to rate-skipped frames are accumulated into the next saved page.

For hierarchical storage of images with many analysis arrays, HDF5 with extendible datasets is another option. BigTIFF was chosen here because existing dependencies support it on Windows and it is convenient for Python image processing. Validation passed 34 Linux and 26 Windows MSVC tests. With display averaging set to three frames, the GUI recorded 13 raw uint16 frames at no more than 5 fps, which were read back in Python. Files written on Windows were also read successfully by Python on Linux.

15. Cooling monitoring and telemetry (Telegraf / Grafana)

15.1 Why sensor temperature alone is insufficient

Status's temperature_c, shown in the GUI, comes from GetTemperatureF and is the CCD sensor temperature, not the heat-sink temperature. The iXon3 hardware guide, section 1.3.7 “Overheating”, describes a thermal switch on the heat sink that cuts TE cooler power and sounds a buzzer above its threshold. Cooling resumes automatically when the head cools. The switch has a limited operating-cycle lifetime, so avoid conditions that repeatedly trip it. Causes include blocked vents, inadequate or stopped water flow, and room temperature above 30 °C.

This switch cannot be read through the SDK, based on inspection of disassembled SDK 2.103 libandor.so on 2026-10-23.

  • GetTECStatus, which reports TEC overheating, and GetFrontEndStatus are iVac-only and return DRV_NOT_SUPPORTED on iXon.
  • The internal overtemperature-trip reader, Micro::TempTripState, applies only to iVac, iVac CCD, and iKon-XL. The OverTempFlag and HeatSinkSensor registers appear only in USB-camera code paths.

The sensor can therefore appear normal briefly after a trip; loss of cooling becomes visible only after it warms. Monitoring uses two complementary checks:

  1. Head temperature and TE cooler voltage: for iXon's 8-bit cooling controller, GetTemperatureStatus, marked “RESERVED” in the manual, reads the cooling-control circuit's ambient temperature over I2C from TemperatureDACAmbient using an LM60-equivalent conversion, and TE cooler voltage from TemperatureDACCoolerVoltage at 0.03 V/LSB. These are read-only operations. The backend probes once at startup and, if supported, reads every 2 seconds. During acquisition it does so only on cameras supporting temperature reads while acquiring. Results appear in the thermal readouts: log and get_info fields has_ambient_temperature, has_cooler_voltage, and thermal_probe. Unsupported readings are null.
  2. Loss-of-cooling alarm (ThermalWatch): once an enabled cooler has brought the sensor within 3 °C of the target, temperature above target + cooling_lost_margin_c (default 5 °C) raises alarm. SDK drift status or an unreadable sensor temperature produces warning. Changing the target or disabling cooling resets target attainment; loss-of-cooling evaluation waits for the target to be reached again. Each state transition logs once: [error] thermal alarm: cooling lost: ..., [warning] thermal warning: ..., or [info] thermal state normal again.

Additional status fields are target_temperature_c, fan_mode, ambient_temperature_c, cooler_voltage_v, tec_overheat (unavailable values are null), thermal_alarm (ok / warning / alarm), thermal_alarm_reason, and thermal_alarm_count, counting entries into alarm since startup. Monitoring does not automatically stop cooling or otherwise change camera state.

Telemetry sends InfluxDB line protocol by HTTP POST to Telegraf's http_listener_v2, using the same format as the /opt/labtime time monitor. A host tag is added automatically; nanosecond timestamps reflect when status was sampled. Sending runs on a dedicated thread and never blocks the camera thread. During outages, up to 4320 points are retained, equivalent to 6 hours at 5-second intervals, and sent together on the next successful attempt. Failures are logged initially and every 10 minutes while continuing. --no-telemetry temporarily disables sending.

In VictoriaMetrics, series are named andor_emccd_<field>{db="laserlab", host="LaserLabLinux1", device="emccd", ...}; Telegraf maps tlg_bucket to the db label. When the camera is disconnected, only state is sent. Unavailable values are omitted rather than replaced with stale readings.

15.4 Verification

A simulator configured with AEC_SIM_TRIP_AT_S=45 trips its switch 45 seconds after startup for 60 seconds. With a local HTTP receiver, testing on 2026-10-23 verified 150 points over 150 seconds, voltage dropping to 0 V and head temperature rising during the trip, exactly one thermal alarm: cooling lost entry when the sensor crossed target +5 °C, and normal again on recovery. test_telemetry covers alarm decisions, line-protocol escaping, URLs, HTTP success/errors, outage buffering, and engine telemetry.

Real camera, 2026-10-23, water cooling, −80 °C target: startup logged thermal readouts: GetTemperatureStatus: sensor -79.25 C, target -79.90 C, ambient 37.45 C, cooler 7.32 V; GetTECStatus: DRV_NOT_SUPPORTED. The sensor reading matched GetTemperatureF at -79.247 °C, validating the conversion. Readings are 8-bit, with steps of 0.65 °C for the sensor, 1.58 °C for the head, and 0.03 V for voltage. Twelve series reached VictoriaMetrics through Telegraf approximately every 5 seconds. Immediately after restart, the sensor varied by about ±2 °C for two minutes (-79.9 → -77.9 °C, not_stabilized), then returned to stabilized at -79.25 °C. The head was at 37–39 °C.

Changing the target from -80 to -75 °C at 18:25 lowered head temperature from about 42 to 39 °C within a minute, while cooler_voltage_v rose slightly from 7.29 to 7.35 V, briefly reaching 7.53 V immediately after the change. This behaves like the TE cooler supply voltage with a slight load-dependent drop, rather than a cooling duty fraction. Interpreting a value near the register maximum of 7.65 V as maximum cooling effort was incorrect. Head temperature is a better load indicator. After a restart at -80 °C, the head warmed from 37 to 42 °C over about 20 minutes, possibly because its circuitry had been power-cycled. A future trip must establish whether this voltage drops to 0 V or rises to an unloaded level near 7.5 V.

16. Floating-point electron/photon display and settings metadata (v0.3.0)

Select Counts / Electrons / Photons under Display units in the Display conversion tab. Camera calibration uses SDK GetSensitivity and GetQE. RealGain uses the gain setpoint, and EM off uses nominal unity gain; metadata distinguishes these from independently measured physical gains. If physical gain is unknown in DAC/Linear mode or the SDK cannot supply coefficients, switch to Manual coefficients and enter Sensitivity (e⁻/ADU), Physical EM gain, QE (%), and Baseline (ADU). Switching from Camera calibration to Manual lets you edit the last displayed coefficients.

The conversion is electrons = (raw − offset) × sensitivity / EM gain, and photons = electrons / QE, with QE expressed from 0 to 1. With a background ROI, that frame's ROI mean replaces offset; the baseline is not subtracted twice. Set the camera's SDK conversion (integer) to Counts. Display conversion uses float32 and preserves fractional and negative values. Normal Save frame / Record / Stream recording preserve the original pixels. Save converted exports float32 TIFF/FITS/NPY after averaging, background correction, and unit conversion, before colormapping or thresholding. ROI statistics, formulas, and UDP output remain in raw units. Converted values are estimates; coefficients alone do not establish exact integer photon counts.

Each raw TIFF page's analysis records background ROI coordinates, mean, and pixel count, plus GUI settings, applied coefficients, and conversion formulas. Metadata is also stored in FITS/PNG JSON tags and NPY .npy.json sidecars. When exporting older backend frames, metadata explicitly identifies GUI settings as a snapshot taken at save time. New backend frame headers also contain camera settings from acquisition time.

Each connected GUI publishes its display, calibration, ROI, formula, UDP, trend, window-layout, and other settings to the backend. BLACS saves the snapshot taken during transition to buffered mode as JSON at data/<device>/camera/images/gui_settings_snapshot. The micro0 and gen0 GUIs have separate profiles, including source and update time. Camera-derived coefficients are refreshed using the actual shot settings, and per-frame background means and conversion details are saved in frame_display_metadata. Raw images are saved as Counts, with PNG/HDF5 previews. This is a runtime record, not a compile-time record. Settings are unavailable for GUIs that have not connected since the backend started. If an older backend lacks the settings-snapshot API, the metadata records that limitation and raw acquisition continues.
